# V0.6 Sprint Backlog

## Goal

V0.6 evolves the system from "manual recognition rail with foundation taxonomy" (V0.5.x) to "live source-of-truth integration with structured leak detection and operational orchestration."

The sprint has three intertwined themes:

- Live sync from Anchor, FC, and QBO replaces static seeds.
- Verdict-driven leak detection gains proper agreement-state awareness.
- Operational orchestration adds pipeline runs, run logs, and dashboard surfaces.

## Probable Sub-Slice Decomposition

This is the working frame for V0.6 planning. Final decomposition will be decided during the V0.6 spec.

- V0.6.A — Data Foundation Layer: live sync extensions for Anchor agreement status, FC tags, QBO products, and canonical service alias resolution.
- V0.6.B — Verdict-Driven Leak Detection: 9-verdict taxonomy in DB, classification persistence, and leak surface UI.
- V0.6.C — Pipeline Orchestration: scheduled Recognition Pipeline, on-demand refresh button, and run log surface.
- V0.6.D — SLA Management Dashboard: per-staff workload, per-client SLA status, and breach detection.

### Verdict Taxonomy

- `INTERNAL_FAMILY` — Saez family, SBC; permanent suppress.
- `PENDING_ENGAGEMENT_DRAFT` — Anchor agreement DRAFT, not sent.
- `PENDING_ENGAGEMENT_SENT` — Anchor agreement SENT, awaiting client.
- `ENGAGEMENT_DECLINED` — Client declined this period (year-aware).
- `LEGITIMATE_LEAK` — No agreement, work being done.
- `BILLING_OUTSIDE_AUDIT_WINDOW` — Active agreement; annual cycle or first cycle not yet due.
- `BILLING_SETUP_GAP` — Active agreement for recurring service; recurring invoices not firing.
- `GROUP_DEFINITION_GAP` — Group's actually-billed parent missing from group definition.
- `MIXED` — Partial billing pattern, case-by-case.

Likely slice: V0.6.B.

### Verdict Logic Requirements

- Audit reads Anchor agreement status and last invoice date for each FC client, not just invoice presence.
- Service-type-aware audit window: 180 days for monthly recurring, 365 days for annual tax-only.
- Year-aware classification for `ENGAGEMENT_DECLINED` (`declined_for_TY:2025` vs. permanent).
- Re-emergence detection: classified row with new FC tasks is flagged for reclassification.
- Aging signal: days since state change (`SENT > 60` = follow-up; `> 90` = stale).
- Verdict persistence: once classified, suppress from default audit view unless state changes.
- Bulk classification UI: checkboxes plus dropdown for fast triage. → V0.6.B

### Manual Recognition UI Improvements

- Header UI tightening: edge margin issues and "Recognition patterns" help section placement need polish. Move from inline-with-table-header to a more discreet location (info icon, sidebar, or header subtitle). Polish edge padding and margins across the page.
- Service column too coarse: currently shows macro service type (`tax`, `bookkeeping`, `payroll`, etc.). The FC service tag should be visible (`S 1120P`, `S BOOKE`, etc.), using `profit_service_recognition_rules.fc_tag` from V0.5.2.1. Add as either a separate column or inline subtitle under service.
- Sort options: enable sortable columns for `source_amount` (numeric desc/asc) and service (`fc_tag` or macro). Currently no sort.
- Status column is low-signal: showing "Pending [service]" duplicates the service column. Either delete the column or enrich it with meaningful internal status (`pending_30d`, `pending_60d`, `pending_with_cash_allocated`, `pending_no_cash`).

Likely slice: V0.6.B / V0.6 polish.
